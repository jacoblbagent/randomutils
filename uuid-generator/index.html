About this tool

Which version to use

Version 4 is 122 random bits and nothing else, so an id reveals nothing about when or where it was made, and collisions are pure chance. It is the right default for anything user-visible: a reset token, a share link, a record id.

Version 7 starts with a 48-bit millisecond timestamp. That helps when ids are a database primary key, because inserts land in roughly index order instead of scattering. The cost is that an id reveals its creation millisecond: harmless in most systems, worth thinking about in a public one.

What makes a v7 sort correctly

  • The first 48 bits are a big-endian timestamp, so a byte-wise comparison compares creation time, and sorting the text sorts the time.
  • The next 12 bits are a counter, not random filler. Ids made in the same millisecond would otherwise share a prefix and sort arbitrarily; the counter advances per id, so batches come out in generation order. On overflow the timestamp borrows the next millisecond.
  • The remaining 62 bits are random, and the version and variant nibbles are stamped over the buffer rather than drawn.

Where the randomness comes from

  • crypto.getRandomValues, the source the browser uses for TLS keys, not Math.random, whose output becomes predictable once enough of it is seen.
  • No modulo arithmetic touches the random bytes: the timestamp and the counter occupy their own fields and the rest is used as drawn.
  • Hyphens, braces and case are display only. They change the string, never the 128 bits.

Privacy

The page makes no network request after it loads, so an id has nowhere to go. It leaves only through your clipboard when you press Copy. Closing the tab erases the list; the privacy page covers the rest.
